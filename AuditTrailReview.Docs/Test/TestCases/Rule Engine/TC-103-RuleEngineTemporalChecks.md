# TC-103 – Rule Engine: Temporal Checks (C1–C3)

## Objective
Verify that `ScanResultService.ApplyRulesAndGenerateResults` correctly flags (or does not flag) audit trail rows against the three Temporal Check rules defined in FR-018 (C1–C3): chronological ordering, no future timestamps, and working-hours/weekend restrictions. (Rule C4, time-gap/continuity detection, was removed in a later rule-management round; see `Audit-Trail-Rule-Regulatory-Basis-Review.md`. Its `EngineSettings.TimeGapThresholdDays` setting, initially retained for backward compatibility, was fully removed in a later round along with several other unused settings -- see `Audit-Trail-Rule-Regulatory-Basis-Review.md`.)

## Preconditions
- No database or web server involved: pure in-memory unit tests against `ScanResultService.ApplyRulesAndGenerateResults`.
- Rows are built with the `Row(...)` helper and overridden per test, mainly the `Timestamp`, `ObjectType`/`Object` (for C1), and `Kind` fields.
- Only the rule under test is enabled; the other 18 of the 19 rules stay disabled.
- C3 depends on `EngineSettings`' configured working-hours window, the `AllowWeekends` flag, and the (optional) `WorkdayTimeZone`.

## Test Steps
| Step | Action | Expected Result |
|------|--------|-----------------|
| 1 | Apply rule C1 to a set of rows with ascending timestamps, one with descending timestamps, and one with an out-of-order timestamp mixed in | Ascending case: no `[C1]` finding. Descending case: no `[C1]` finding (auto-detected direction). Out-of-order case: `[C1]` finding on the offending row |
| 2 | Apply rule C1 to rows from two different records (`ObjectType`+`Object`) interleaved in file order, each internally ordered but the file as a whole jumping back and forth in time, then to the same interleaving with one record's own sequence out of order | Neither record is flagged in the first case; only the genuinely out-of-order record's row is flagged in the second, since ordering and auto-detected direction are per-record, not whole-file. Rows with no `Object`/`ObjectType` populated at all collapse into one shared group, reproducing the original whole-file behavior |
| 3 | Apply rule C2 to a row timestamped in the future relative to the system clock, one in the past, and one with a null timestamp | Future case produces a `[C2]` finding; past and null cases do not |
| 4 | Apply rule C2 to `Kind = Local` timestamps built from known-past/known-future UTC instants (via `ToLocalTime()`), to a `Kind = Unspecified` timestamp with no `WorkdayTimeZone` configured, and to a `Kind = Unspecified` timestamp with `WorkdayTimeZone` configured | `Local`-kind past/future are correctly classified after conversion to UTC, deterministically regardless of the machine's own time zone; `Unspecified` with no `WorkdayTimeZone` configured resolves to UTC (unchanged from before); `Unspecified` with a `WorkdayTimeZone` configured is interpreted as already being local plant time in that zone and converted to UTC using its offset before the comparison, rather than compared as written |
| 5 | Apply rule C3 to a row timestamped outside the configured working-hours window, and one inside it | Outside-hours case produces a `[C3]` finding; inside-hours case does not |
| 6 | Apply rule C3 to a weekend timestamp with `AllowWeekends = true`, and with `AllowWeekends = false` | `AllowWeekends = true` produces no `[C3]` finding for the weekend row; `AllowWeekends = false` produces one |
| 7 | Apply rule C3 to `Kind = Local` timestamps evaluated against the working-hours window, and to a `Kind = Unspecified` timestamp with no `WorkdayTimeZone` configured | `Local`-kind is normalized to UTC before the hour/day check, deterministically regardless of the machine's own time zone; `Unspecified` with no `WorkdayTimeZone` configured resolves to UTC (unchanged from before) |
| 8 | Apply rule C3 with `WorkdayTimeZone` set to a specific IANA zone (e.g. `"Europe/Warsaw"`, `"Asia/Tokyo"`), using a UTC instant that falls inside/outside the configured hour window -- and separately on/off a weekend -- only once converted into that zone | Both the hour check and the weekend check follow the configured `WorkdayTimeZone`, not UTC and not the source `Kind`'s own zone |
| 9 | Apply rule C3 with `WorkdayTimeZone` set to an unrecognized/garbage ID | Falls back to evaluating in UTC rather than throwing and failing the scan |
| 10 | Apply rule C3 to a `Kind = Unspecified` timestamp with `WorkdayTimeZone` configured, once inside the working-hours window and once genuinely outside it (regression test for a user-reported bug: an ambiguous 17:00 timestamp was previously assumed to be UTC and shifted forward into the configured zone, crossing the end-of-hours boundary it was never actually near) | The timestamp is assumed to already be local plant time in the configured `WorkdayTimeZone` and evaluated at face value with no conversion: the inside-hours case produces no `[C3]` finding, and the genuinely-outside-hours case still does |
| 11 | Apply rule C3 to an explicit `Kind = Utc` timestamp (with `TimestampRaw` set to a matching ISO-8601 "Z" string) that shifts outside the working-hours window once converted into the configured `WorkdayTimeZone`, and separately to a `Kind = Unspecified` timestamp whose evaluated-at-face-value shift also produces a `[C3]` finding (regression test for a follow-up user report: a fresh, rebuilt scan still showed the same class of shift the step-10 fix was meant to eliminate -- traced to a *legitimate* conversion of an explicitly UTC-marked source timestamp, not a regression, but the finding text didn't say so) | The `Kind = Utc` case's finding names both the parsed `Kind` and the exact `TimestampRaw` source value that produced the conversion (e.g. "Utc kind, from source value '...'"); the `Kind = Unspecified` case's finding never claims a source value backed its shift, since that shift is the engine's own assumption, not something the source data asserted |

## Assertions
- `ScanResultInfo.Finding` contains `[C1]`, `[C2]`, or `[C3]` exactly when the corresponding temporal condition is violated, respecting the configured working-hours/weekend/time-zone settings for C3 and each rule's `DateTime.Kind` handling for C2/C3.
- When a C2/C3 conversion actually changes the wall-clock reading, the finding names the parsed `DateTimeKind`; when that Kind is not `Unspecified` and `TimestampRaw` is available, the finding also names the exact raw source value responsible, via `ScanResultService.FormatRawSourceNote`.
