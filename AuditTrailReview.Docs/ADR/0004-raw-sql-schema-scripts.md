# 0004. Database schema managed via raw SQL scripts, not EF Core migrations

Status: Accepted (contested; see Consequences)
Date: 2026-09-01 (reconstructed from the v0.6 codebase)

## Context
`AuditTrailReview.Database` references EF Core and defines `ApplicationDbContext` with the full entity model (Identity tables, Scan, ScanResult, SystemATR, Rules, EngineSettings, logs, etc.). EF Core supports two common ways to get a matching schema onto a real database: code-first migrations (`dotnet ef migrations add` / `dotnet ef database update`) or a hand-maintained schema applied out of band. Notably, the migrations path was available and apparently tried early on, not just theoretical: old scaffolding notes for the project still contain commented-out `add-migration`/`update-database` Package Manager Console commands targeting `AuditTrailReview.Database`, evidence that EF migration tooling was scaffolded before the project settled on raw SQL scripts instead.

## Decision
The team chose the latter: schema is captured as full, versioned, SSMS-generated "CREATE TABLE" SQL scripts checked into `AuditTrailReview.Database/Database schema/` (e.g. `ATR 0.2 20260218.sql` through `ATR 0.4 20260419_2012.sql`). There is no `Migrations/` folder anywhere in the solution, and `Program.cs` never calls `Database.Migrate()` or `Database.EnsureCreated()`: the application assumes the schema already exists and only seeds *reference data* (roles, the admin service account, rule definitions, system types, engine settings) at startup, not the schema itself.

## Consequences

**Positive:**
- The exact DDL that will run against a production database is visible and reviewable as plain SQL, rather than being generated by tooling at deploy time, which some DBAs/change-control processes prefer for a regulated system.
- No risk of an auto-generated migration silently doing something destructive (e.g. a column rename EF Core can't safely infer) without a human reviewing the actual SQL first.

**Negative / known gaps (this is flagged "contested" because these are real operational risks):**
- **No automated, repeatable path from zero to a running database.** A new environment requires someone to manually identify and run the *latest* schema script (currently `ATR 0.4 20260419_2012.sql`; note that the filename doesn't obviously indicate it supersedes the very similarly named `ATR 0.4 20260419.sql`) rather than running one command. `Installation Manual.md` documents this manual step explicitly because there's no alternative today.
- **No incremental upgrade path.** Since these are full "create from scratch" scripts rather than migrations, there's no documented, automated way to take an *existing* v0.4 database to v0.5/v0.6 schema; only fresh-install scripts exist per version. Upgrading a production database currently appears to require manually diffing schema versions.
- **Documentation drift risk realized:** `Tech/TechStack.md` currently states "EF Core Migrations: database schema is managed via EF Core migrations in the Database project," which is inaccurate as of v0.6 and should be corrected, since it directly contradicts this decision as actually implemented.
- **No down-migration / rollback story** for a bad schema change, beyond restoring from a database backup. ~~(and no backup/DR plan exists yet; see the "Missing documents" discussion in the project's docs backlog)~~ **Backup/DR policy decided, 2026-09-02** (see `ADR-0002`'s "Data retention and backup policy" note): backup/restore is a manual, customer-managed SQL Server DBA procedure by explicit decision, not a gap awaiting a written policy. What remains open here is narrower than the original wording suggested: there's still no automated *schema* down-migration/rollback tooling (see the alternatives below), independent of how backups themselves are taken.

## Update (2026-10-19): incremental scripts, and the current install order
The two "no repeatable path" and "no incremental upgrade path" gaps above were partly closed after v0.7 without changing the decision:
- `ATR 0.7 20260910.sql` (with a `-SQL2012` variant) was the full snapshot at the time of this update; it was superseded by `ATR 0.8 20261020` (SQL2012 and SQL2025 variants), which folded in the incremental scripts that had been numbered `0.20`-`0.24` then.
- Later schema changes are small **incremental scripts** numbered `ATR 0.20` and above again, restarting after the 0.8 snapshot (`0.20` drops `EngineSettings.ReasonMinAlphabeticChars`, `0.21` adds `ScanFile`, and so on up to `0.40` adding `FtpConfiguration` at v1.0). They are applied by hand in **version order** (sort by number, not file name: `0.7` sorts after `0.20` alphabetically) on top of the `0.8` snapshot, or on top of an older database that predates them. See `Installation Manual.md` section 3 for the exact list and what each one changes.
- There is still no automated runner, no rollback script and no check that a database is at the expected version. A schema change still means a new numbered script **and** a matching change to the entity and `ApplicationDbContext`.
- The SQLite and PostgreSQL evaluation flavors (ADR-0009) do not use these scripts at all; they build the schema from the EF model at startup.

## Alternatives considered
- **EF Core code-first migrations**, generated from the `ApplicationDbContext` model and applied via `dotnet ef database update` or `Database.Migrate()` at startup. Would give an automated, incremental, and rollback-capable upgrade path, and would keep the SQL in sync with the C# model by construction. This is the recommended direction if the "contested" status above is to be resolved before v1.0; it does not require abandoning reviewable SQL, since `dotnet ef migrations script` can still produce a reviewable `.sql` file from a migration for change-control sign-off.
