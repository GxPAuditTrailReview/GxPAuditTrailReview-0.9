# 0007. ASP.NET Core Identity with a three-role model (Admin / Super User / User)

Status: Accepted
Date: 2026-09-01 (reconstructed from the v0.6 codebase)

## Context
The product needs authenticated access with some notion of privilege separation: routine reviewers shouldn't need the same access as someone configuring the rule engine or administering accounts, per typical GxP segregation-of-duties expectations. ASP.NET Core Identity was added to `AuditTrailReview.WebApp` via Visual Studio's built-in Identity scaffolder (Add New Scaffold Item → Identity), which is why the Identity Razor Pages under `Areas/Identity` follow the standard template layout rather than being hand-written. No external/social login providers are configured; only local email/password accounts exist (see `3 Functional & Configuration Specification.md` NFR-001).

## Decision
Use ASP.NET Core Identity (`AddDefaultIdentity<IdentityUser>().AddRoles<IdentityRole>()`) for authentication, backed by the shared database. Three roles are seeded automatically on startup: **Admin**, **Super User**, **User**. A seed Admin account is created from `SeedAccount:Email`/`SeedAccount:Password` configuration the first time the app starts against an empty user table.

**Role scope, confirmed 2026-09-01, narrowed 2026-10-27 (see the "Scope change" entries below):** Admin has full administrative access: all of Admin Panel (`AdminPanel/User/*`, `AdminPanel/Role/*`, `AdminPanel/Settings/*`, `AdminPanel/AIEnhancedReviewEngine`, `AdminPanel/DocsChatbot`) plus Config Panel. Super User's privilege is scoped to the two configuration pages that remain in Config Panel -- `ConfigPanel/RuleBasedReviewEngine` and `ConfigPanel/SystemType/*` -- plus reopening or deleting a scan, and deleting a system, on top of the standard authenticated-user baseline; Admin Panel is Admin-only and out of reach for Super User entirely. Scan review and sign-and-close, and system create/edit/view, are intentionally available to any authenticated user regardless of role, User included, and are not treated as privileged actions under this model. This confirms and supersedes the earlier, less specific intent in `ReleaseNotes/RN v0.4.md` ("reopen a scan if the user has Key User or Admin roles") -- that note captured a stated intent at the time; the decision recorded here is the current, deliberate scope.

**Documentation correction, 2026-10-27:** `Product/User manual.md`'s role-summary table previously listed "privileged review actions" under Super User, which contradicted the Role scope decision above -- confirmed by re-reading every `[Authorize]` attribute in `AuditTrailReview.WebApp/Pages`: scan review and sign-and-close (`Pages/Scan/Details.cshtml.cs`) carry a plain `[Authorize]` with no role restriction, same as system CRUD. That phrase has been removed, and the manual's one-line summary table is now followed by a full per-action permissions matrix (sign-in/dashboard/help, systems, scans, each Config Panel page, and each Admin Panel page) so "what can each role do" is answerable without reading code.

**Scope change, 2026-10-27: reopening a signed scan now requires Admin or Super User.** Per the user's explicit request, a plain `User`-role account must no longer be able to reopen (undo the electronic signature on) a closed scan. This narrows the "every operational action is open to any role" position above: scan review and sign-and-close remain open to any signed-in role, but reopen does not. `Pages/Scan/Details.cshtml.cs`'s `OnPostReopenAsync` now starts with an explicit `if (!User.IsInRole("Admin") && !User.IsInRole("Super User")) return Forbid();` rather than a page-level `[Authorize(Roles = "...")]` attribute, because `Scan/Details` is a single page shared by many handlers (view, review, sign-and-close, assign system, download, export, reopen) that must stay open to every role -- only this one handler needed gating. The "Reopen review" button in `Pages/Scan/Details.cshtml` is likewise now rendered only for `User.IsInRole("Admin") || User.IsInRole("Super User")`, matching the `IsInRole`-based UI-hint pattern already used elsewhere on this page and in `System/Create.cshtml`/`System/Edit.cshtml`. Covered by `AuditTrailReview.UnitTest/WebApp/Scan/DetailsModelTests.cs` (`OnPostReopenAsync_PlainUserRole_ReturnsForbidAndLeavesScanClosed`, `OnPostReopenAsync_NoRole_ReturnsForbidAndLeavesScanClosed`, `OnPostReopenAsync_SuperUserRole_ReopensScan`).

**Scope change, 2026-10-27: deleting a scan now requires Admin or Super User.** Per the same request, a plain `User`-role account must no longer be able to permanently delete a scan (and its `ScanResult`/`ScanResultAI` rows -- unlike Reopen, this is not reversible from within the app). Unlike `Scan/Details`, `Pages/Scan/Delete.cshtml.cs` is a single-purpose page (its `OnGetAsync` shows the delete confirmation, `OnPostAsync` performs the delete, nothing else), so it carries the attribute directly: `[Authorize(Roles = "Admin,Super User")]` at the class level, the same pattern already used for `AdminPanel/User/*`, `AdminPanel/Role/*`, and `ConfigPanel/SystemType/*`. The two places that link to this page -- the scan list's delete icon (`Pages/Scan/Index.cshtml`) and a system's scan list (`Pages/System/Details.cshtml`) -- now also check `User.IsInRole("Admin") || User.IsInRole("Super User")` before rendering that icon, on top of the existing `!item.ScanClosed` check. As with every other attribute-restricted page in this codebase, the restriction is enforced by ASP.NET Core's authorization middleware rather than inside the handler, so (consistent with e.g. `AdminPanel/User/IndexModelTests.cs`) the existing `DeleteModelTests.cs` unit tests -- which call `OnGetAsync`/`OnPostAsync` directly and never go through that middleware -- did not need role-specific additions; they continue to verify the handler's own delete logic.

**Scope change, 2026-10-27: deleting a system now requires Admin or Super User.** Per the user's explicit request, a plain `User`-role account must no longer be able to permanently delete a system (and implicitly orphan any scans still pointing at it via `SystemID`). `Pages/System/Delete.cshtml.cs` is a single-purpose page (`OnGetAsync` shows the delete confirmation, `OnPostAsync` performs the delete), so -- same pattern as `Pages/Scan/Delete.cshtml.cs` -- it now carries `[Authorize(Roles = "Admin,Super User")]` at the class level instead of a plain `[Authorize]`. The only place that links to it, the delete icon in `Pages/System/Index.cshtml`'s action column (there's no gating `!item.X` condition here, unlike Scan's `!item.ScanClosed`), now also checks `User.IsInRole("Admin") || User.IsInRole("Super User")` before rendering. System create/edit/view (`System/Create`, `System/Edit`, `System/Details`, `System/Index` itself) remain a plain `[Authorize]`, open to any role -- only delete is restricted. As with `Scan/Delete`, the existing `AuditTrailReview.UnitTest/WebApp/System/DeleteModelTests.cs` unit tests call `OnGetAsync`/`OnPostAsync` directly and never go through the authorization middleware that enforces this attribute, so none needed role-specific additions.

**Scope change, 2026-10-27: Application Settings moved from Config Panel to Admin Panel (access narrowed later the same day -- see the next entry).** Per the user's explicit request, `Pages/ConfigPanel/Settings/*` (`Index`, `Edit`, `EditGeneral`, `EditEmail`, `EditAI`) moved to `Pages/AdminPanel/Settings/*`, changing its URL from `/ConfigPanel/Settings/...` to `/AdminPanel/Settings/...` and its namespace from `AuditTrailReview.WebApp.Pages.ConfigPanel.Settings` to `AuditTrailReview.WebApp.Pages.AdminPanel.Settings`. At the time of this move access was left unchanged (`Index`/`EditGeneral`/`EditEmail`/`EditAI` still `[Authorize(Roles = "Admin,Super User")]`, `Edit` still `[Authorize(Roles = "Admin")]`), with the Admin Panel dropdown's visibility widened to `Admin || Super User` so Super User could still reach it from the nav. Internal links from these pages to the two Config-Panel pages that did *not* move at this point (`ConfigPanel/AIEnhancedReviewEngine`, `ConfigPanel/RuleBasedReviewEngine`) were left unchanged. No unit tests exist for these pages (none are listed under `AuditTrailReview.UnitTest/WebApp/ConfigPanel`), so none needed updating.

**Scope change, 2026-10-27 (same day): AI Analysis and Docs chatbot also moved to Admin Panel, and Admin Panel became Admin-only throughout.** Per the user's explicit follow-up request ("Admin Panel should generally be accessible only to Admin role"), two more pages moved: `Pages/ConfigPanel/AIEnhancedReviewEngine.cshtml[.cs]` → `Pages/AdminPanel/AIEnhancedReviewEngine.cshtml[.cs]` and `Pages/ConfigPanel/DocsChatbot.cshtml[.cs]` → `Pages/AdminPanel/DocsChatbot.cshtml[.cs]` (namespace `AuditTrailReview.WebApp.Pages.ConfigPanel` → `...Pages.AdminPanel` for both). At the same time, every page under Admin Panel -- the two pages just moved, and the Settings pages from the entry above -- had its `[Authorize(Roles = "Admin,Super User")]` narrowed to `[Authorize(Roles = "Admin")]`; `Settings/Edit` (security policy) was already Admin-only and is unchanged. This supersedes the "access is unchanged" and "Super User must still reach it" statements in the entry above for the Settings pages specifically: Super User lost both nav visibility and page access for Application Settings, AI Analysis, and Docs chatbot in this second step. `_Layout.cshtml`'s Admin Panel dropdown visibility was narrowed back to `User.IsInRole("Admin")` only (dropping the `|| Super User` added minutes earlier), now listing Users, Roles, Application settings, AI Analysis, and Docs chatbot together, all Admin-only, with no further per-item role checks needed. The Config Panel dropdown lost its AI Analysis and Docs chatbot entries, leaving only Rule-based review engine and System type -- the two pages Super User still reaches. `Pages/Scan/Details.cshtml`'s "AI-enhanced review engine" link (shown when AI analysis is globally disabled) is now gated on `User.IsInRole("Admin")` only, matching the page's new access level, instead of `Admin || Super User`. `AuditTrailReview.UnitTest/WebApp/ConfigPanel/AIEnhancedReviewEngineModelTests.cs` moved to `AuditTrailReview.UnitTest/WebApp/AdminPanel/AIEnhancedReviewEngineModelTests.cs` (namespace updated to match); no DocsChatbot unit tests exist to move. `TC-753` (`AuditTrailReview.Docs/Test/TestCases/WebApp Admin Panel/TC-753-AdminPanelAIEnhancedReviewEngine.md`, moved from the `WebApp Config Panel` folder, same TC id) and `Matrix-TestCases-Tests.md` were updated to match. Post-change role map: **Admin** reaches everything; **Super User** reaches only `ConfigPanel/RuleBasedReviewEngine` and `ConfigPanel/SystemType/*` beyond the authenticated-user baseline (plus scan reopen/delete, per the entries above); **User** reaches only the authenticated-user baseline.

**Scope change, 2026-11-05: AI Analysis page merged into Application Settings' AI Analysis tab.** Per the user's explicit request, the standalone `Pages/AdminPanel/AIEnhancedReviewEngine.cshtml[.cs]` page introduced above (the `EngineSettings.AiAnalysisEnabled` on/off toggle plus the read-only prompt-template display) was deleted outright, and its functionality folded into `Pages/AdminPanel/Settings/Index.cshtml[.cs]`'s existing AI Analysis tab -- the toggle is now saved together with `AiSettings` by that tab's own `OnPostSaveAiAsync` handler (via a new `SaveAiAnalysisEnabledAsync` helper), and the prompt template moved into the same tab as a second read-only card. Access is unchanged: this functionality is still Admin-only, since `AdminPanel/Settings/Index` was already `[Authorize(Roles = "Admin")]`, same as the deleted page. The Admin Panel dropdown's separate "AI Analysis" menu item (`_Layout.cshtml`) was removed -- Application Settings' own entry now covers it -- and `Scan/Details.cshtml`'s "AI analysis is currently disabled" link now points at `AdminPanel/Settings/Index?ActiveTab=ai` instead of the deleted page. The Settings page's Audit Trail tab's AI sub-tab now also includes the toggle's own history (`EngineSettings`/`AiAnalysisEnabled`, alongside `AiSettings` changes, via `IndexModel.LoadAuditTrailSubTabAsync`'s predicate for that sub-tab), and `IndexModel.OnGetExportAllAsync`'s AI Analysis sheet gained an "AI Analysis Enabled"/"Prompt Template" row pair, with the toggle's audit rows included in the export's combined Audit Trail sheet (labeled "AI Analysis" there too). `AuditTrailReview.UnitTest/WebApp/AdminPanel/AIEnhancedReviewEngineModelTests.cs` was deleted; its coverage was ported into `WebApp/AdminPanel/Settings/IndexModelTests.cs`. `TC-753` was merged into `TC-703-AdminPanelSettingsAuditTrail.md` and deleted; `Matrix-TestCases-Tests.md` and `Matrix-IQOQ-UAT-TC-TestAutomation.md` were updated to match.

## Consequences

**Positive:**
- Standard, well-understood, cookie-based authentication with hashed password storage, no custom auth code to maintain or audit for correctness.
- Role infrastructure (role table, per-user role assignment via `AdminPanel/User/Create`) is fully in place and ready to be used for finer-grained checks.
- Login/logout events are captured automatically via `IUserActivityLogService` regardless of which role signed in.

**Negative / known gaps (historical: all since resolved, resolved by decision, or removed from scope; see each bullet):**
- ~~Only one area actually checks role membership...~~ **Fixed, and scoped by decision.** `AdminPanel/User/*` and `AdminPanel/Role/*` carry `[Authorize(Roles = "Admin")]`, and `ConfigPanel/RuleBasedReviewEngine` / `ConfigPanel/SystemType/*` now carry `[Authorize(Roles = "Admin,Super User")]` -- the Config Panel navigation link in `_Layout.cshtml` is likewise now shown only to those roles, which in the process fixed a pre-existing case-mismatch bug where the link-visibility check tested for role `"Super user"` instead of the actually-seeded `"Super User"`, so it never matched a real Super User account. Scan review/sign-and-close, system create/edit/view, and logs still use a plain `[Authorize]` -- confirmed as intentional (see "Role scope" above), not an open gap: those are operational actions available to any authenticated user by design. Scan reopen, scan delete, and system delete are the exceptions: as of the 2026-10-27 scope changes above, `OnPostReopenAsync` adds its own in-handler `Admin`/`Super User` check on top of `Scan/Details`'s plain `[Authorize]`, and `Scan/Delete`/`System/Delete` each carry `[Authorize(Roles = "Admin,Super User")]` outright instead of a plain `[Authorize]`.
- ~~Two pages have no authorization attribute active at all: `System/Create` and `System/Index` (the `[Authorize(Roles = "Admin")]` attribute is present in the source but commented out), so they don't even require sign-in.~~ **Fixed** (found already resolved during a later documentation revision; see `Path to v1.0.md` item 4). Both pages now carry a plain, active `[Authorize]`, which is now confirmed as the intended state for system CRUD (see "Role scope" above), not a stand-in for a role-restricted attribute that was still meant to be added.
- ~~The "Super User" role confers no additional privilege over "User" for scan review/sign/reopen and system CRUD, despite release notes describing Reopen Scan as intended for "Key User or Admin roles".~~ **Resolved -- partly by decision, partly (reopen) by a later code change.** Confirmed 2026-09-01 that Super User's privilege being Config-Panel-only was the intended scope for review/sign-and-close/system CRUD (see "Role scope" above); `ReleaseNotes/RN v0.4.md`'s earlier wording is left as-is (release notes are a point-in-time record) but no longer reflects the current design. Reopen specifically changed on 2026-10-27 (see "Scope change" above) to require Admin or Super User, which is now consistent with that release note's original intent for this one action.
- ~~No password policy customization: `AddDefaultIdentity` is used without setting `IdentityOptions.Password`, so the framework's out-of-the-box default policy applies (minimum 6 characters, requires a digit, lowercase, uppercase, and non-alphanumeric character) rather than an organization-specific policy.~~ **Fixed.** `Program.cs` now sets `IdentityOptions.Password` explicitly: `RequiredLength = 8` (the org's stated minimum for now), with `RequireDigit`/`RequireLowercase`/`RequireUppercase`/`RequireNonAlphanumeric` kept at their previous default values so the change is scoped to length only, as requested. `Register.cshtml.cs`'s client-side `[StringLength(MinimumLength = ...)]` was updated to match (8), so the UI hint and the actual server-enforced rule agree.
- ~~No account lockout is enforced on login failure (`lockoutOnFailure: false` is passed explicitly in `Login.cshtml.cs`'s `PasswordSignInAsync` call), and no MFA is configured.~~ **Lockout fixed; MFA removed from requirements scope.** `Program.cs` now sets `IdentityOptions.Lockout.MaxFailedAccessAttempts = 3` (the org's stated threshold), with `DefaultLockoutTimeSpan` left at the framework default of 5 minutes since only the attempt count was specified. `Login.cshtml.cs` now passes `lockoutOnFailure: true` -- without that flag the lockout options above would be configured but never actually applied, since `PasswordSignInAsync` only counts failures toward lockout when asked to. A lockout event is now also recorded via `IUserActivityLogService` (`action: "AccountLockedOut"`), consistent with how `Login`/`LoginFailed` are already logged. MFA has been removed from requirements scope at the user's explicit request (2026-09-02) -- it is not tracked as an open gap; it may be introduced in a future phase if the organization decides it's needed.

## Alternatives considered
- **Policy-based authorization** (`AddAuthorization` with named policies mapped to roles, e.g. `"RequireAdminOrSuperUser"`) instead of inline `[Authorize(Roles = "...")]` attributes. Would centralize the role list in one place rather than repeating `"Admin,Super User"` per page (and per in-handler `IsInRole` check, now that `OnPostReopenAsync` has one too), at the cost of an extra layer of indirection for a model this small (two role-gated tiers today). Revisit if a third role-gated tier is added. Scan review/sign-and-close and system create/edit/view are no longer in scope for this either way, per the "Role scope" decision above.
- **Claims-based fine-grained permissions** instead of three fixed roles. Rejected as more flexible than needed for the current three-tier model; revisit only if role requirements grow more granular than Admin/Super User/User.
