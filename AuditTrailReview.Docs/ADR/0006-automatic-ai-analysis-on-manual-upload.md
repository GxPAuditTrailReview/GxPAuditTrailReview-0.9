# 0006. Automatic AI-assisted analysis on manual web uploads

Status: Accepted, originally synchronous and contested (see history below); the contested part was fixed by moving the AI call off the request path.
Date: 2026-09-01 (reconstructed from the v0.6 codebase); updated 2026-09-01 when the synchronous design was replaced.

## Context
The 17 deterministic rules catch well-defined, pattern-matchable issues, but the product's vision (per the Prompt notes and PRD) also calls for a broader, GxP/21 CFR Part 11-aware second opinion on an audit trail: the kind of qualitative read a human QA reviewer with domain experience would give, which is hard to express as a fixed rule.

## Decision
After a manually uploaded scan's rule-based results are computed and saved, `Pages/Scan/Scan.cshtml.cs` queues the AI analysis call onto a background hosted service (`AuditTrailReview.Engine.BackgroundTasks.QueuedHostedService`, backed by `IBackgroundTaskQueue` -- moved here from `AuditTrailReview.WebApp` once the Worker Service and API needed their own instances of the same mechanism too, see the now-resolved "Asymmetric with the other ingestion paths" gap below) and returns immediately: it no longer waits for OpenAI before completing the upload request. The queued work item, running on its own DI scope with a 60-second timeout, instantiates `OpenAIService` and calls `QueryJsonWithPromptAsync`, sending ~~the full scan-result JSON~~ **(changed 2026-10-27, see the payload-tiering gap below)** a tiered payload -- the scan's ENTIRE row set when it has `AiSettings.FullScanRowThreshold` rows or fewer, or otherwise a capped, evenly-sampled set of its rule-engine findings (rows with a non-empty `Finding`, capped at `AiSettings.MaxFindingsPerAnalysis`) plus a whole-scan statistical summary -- and a fixed GxP-focused system/user prompt to OpenAI's Chat Completions API (`gpt-4o-mini`). The parsed `insights`/`recommendations` are stored as a `ScanResultAIInfo` row, whenever the call succeeds, and surfaced in the scan's AI Analysis tab and Excel export the next time either is loaded. The call is skipped entirely when `EngineSettings.AiAnalysisEnabled` is off (see the "No opt-out" gap below, now resolved) -- it otherwise always runs, for every manual upload, findings or not, since the whole point of the AI step is to catch what the rule engine doesn't -- and `OpenAIService`'s constructor still throwing on a missing API key is caught inside the background item instead of propagating to the user.

**Original design (superseded):** the AI call used to run synchronously, inline in the same request that saved the rule-based scan, before this decision was amended per the "Make the AI step optional and asynchronous" alternative below.

## Consequences

**Positive:**
- Every manually reviewed scan automatically gets a supplementary AI read with zero extra action from the reviewer.
- The prompt is explicitly framed around GxP/21 CFR Part 11 audit-trail review, giving domain-relevant framing rather than a generic "summarize this JSON" request.
- (New) A missing/invalid OpenAI key, a slow response, or any other AI-side failure no longer affects the manual-upload request at all: the rule-based scan-save and the AI step are now genuinely two independent request/response cycles rather than one.

**Negative / known gaps:**
- ~~A missing or invalid OpenAI API key breaks the entire manual-upload request~~ **Fixed.** The AI call now runs in the background, after the request has already returned; any failure there (missing/invalid key, network error, malformed response) is caught and logged in the background item and never surfaces as a failed upload.
- ~~The call is synchronous and unbounded in latency~~ **Fixed.** The manual-upload request's response time is no longer affected by OpenAI at all. The background item itself is now bounded by a 60-second timeout, so a hung OpenAI request cannot occupy the background queue's single worker indefinitely either.
- ~~**No opt-out.** Organizations that don't want audit trail data sent to a third-party AI service for regulatory, contractual, or data-residency reasons currently cannot use the manual-upload path at all without disabling AI at the infrastructure level (e.g. blocking egress to `api.openai.com`), which would now simply make every manual upload's background AI step fail silently (logged, not user-facing) rather than fail the upload, which is an improvement, but a real opt-out toggle is still not implemented.~~ **Fixed.** A new `EngineSettings.AiAnalysisEnabled` flag (default `true`, preserving prior behavior) stops `Scan.cshtml.cs`'s `OnPostAsync` from queuing the background AI work item at all when disabled, not just from failing gracefully. It's exposed as a single on/off toggle, originally on its own `AdminPanel/AIEnhancedReviewEngine` page (`[Authorize(Roles = "Admin,Super User")]`, matching Rule-Based Review Engine's access), later merged into `AdminPanel/Settings`' AI Analysis tab -- see ADR-0007's 2026-11-05 entry -- audited the same way rule enablement and other engine settings changes are (`IAuditTrailService`, `AuditObjectType.ConfigPanel`). This resolves FR-037's "make the AI call optional" half; the prompt/model configuration half of that FR is still not implemented; see FR-037 for what remains open there. Disabling the toggle does not delete or hide AI results already saved for past scans, only stops new ones from being generated; `Scan/Details.cshtml.cs`'s AI Analysis tab now shows a distinct "AI analysis is currently disabled" message (linking to the config page for Admin/Super User viewers) instead of the neutral "no AI analysis available" message, so a reviewer can tell the difference between "never ran" and "turned off".
- ~~**Asymmetric with the other ingestion paths.** Worker Service and API-ingested scans never get this analysis, so the AI Analysis tab's presence/emptiness silently reveals which ingestion path a scan came from, which may be surprising to reviewers who don't know that distinction exists.~~ **Fixed.** Per an explicit product decision (`Path to v1.0.md` item 28), `ScanProcessingService.ProcessFileAsync` -- the pipeline shared by the Worker Service and API -- now queues the same background AI-analysis work item the manual-upload path does, gated on the same `EngineSettings.AiAnalysisEnabled` flag. All three ingestion paths are symmetric now: every scan, regardless of how it arrived, gets an AI Analysis tab result whenever the flag is on. See the Alternatives section below and `Path to v1.0.md`'s Thirty-seventh follow-up for the implementation detail.
- **The prompt and model are hard-coded** (`gpt-4o-mini`, a fixed system/user prompt) with no admin-facing configuration, despite the PRD's "AI Configuration Placeholder" section anticipating this would eventually be configurable. (Partially narrowed 2026-10-27: `AiSettings.FullScanRowThreshold`/`MaxFindingsPerAnalysis` are now admin-configurable knobs over what data the prompt carries, via `AdminPanel/Settings/EditAI` -- but the prompt wording and model name itself remain fixed.)
- **(New, 2026-10-27) The AI payload is tiered by scan size, not always the full scan.** Previously every row of a scan -- up to ~5,000,000 for a large WebApp/API/FTP upload -- was unconditionally serialized into the OpenAI request, which could take minutes or fail outright regardless of the 60-second timeout. A scan with `AiSettings.FullScanRowThreshold` rows or fewer (default 300) still gets its entire row set sent, unchanged from this feature's original behavior -- the AI keeps full independent-analysis capability for the common case. A scan above that threshold instead gets `ScanResultService.ConvertScanResultsToJson`'s capped overload: only rows where `Finding` is non-empty, capped at `AiSettings.MaxFindingsPerAnalysis` (default 200; `Range(1,1000)`), **evenly sampled across the whole ordered set of findings (first, last, and spread in between) rather than just the first ones encountered**, plus `ScanResultService.BuildScanStatisticalSummaryJson`'s whole-scan statistics (per-user/per-operation/per-object-type counts, an hour-of-day/day-of-week histogram, missing-reason count) covering every row, sampled or not, computed in one cheap pass over the data already in memory. When the findings are sampled, the prompt includes a note telling the model so, and the statistics section is explicitly framed as covering the *entire* audit trail, so "insights"/"recommendations" don't imply more or less coverage than was actually sent. Both thresholds are **row-count caps, not token/byte caps**: a scan whose included rows happen to have unusually verbose `OldValue`/`NewValue`/`Reason` text can still produce a large payload within either limit -- a known, accepted limitation, not solved here (would need a token counter). A consequence worth naming honestly: for a scan above the threshold, the AI still cannot do a true row-by-row independent scan of the whole audit trail -- no feasible design makes that possible at ~5,000,000 rows -- the statistical summary is a partial mitigation (aggregate signal across every row) for that lost capability, not a full restoration of it. This tiering, and the even-sampling instead of a prefix cut, were explicit, confirmed design choices (not oversights), made specifically so bounding AI-analysis latency wouldn't come at the cost of the AI's independent-analysis value for the vast majority of real, smaller scans.
- **(New, 2026-10-27) The AI call always runs, findings or not, in both tiers.** An earlier iteration of this change considered skipping the OpenAI call entirely for a scan with zero rule-engine findings -- rejected, because it would defeat the whole premise of this ADR (an independent read that can catch what the rules don't) for exactly the scans where that independence matters most: ones clean by the rules' own checks.
- ~~No UI signal that AI analysis is still pending~~ **Fixed.** The scan Details page now shows a "give us a few seconds" message with a spinner on the AI Analysis tab, and polls `DetailsModel.OnGetAiAnalysisAsync` every 5 seconds (client-side, `Details.cshtml`'s script section) to swap the real table in automatically as soon as the background result lands, updating the tab's badge count in the same pass, with no manual refresh needed. The "pending" state and the poll are both bounded to a 10-minute window (`DetailsModel.AiAnalysisPendingWindow`), comfortably longer than the AI job's own 60-second timeout; past that window (or on failure), the tab falls back to a neutral "no AI analysis available" message and stops polling. That window is a time-based heuristic, not a persisted flag, and there is still nothing on `ScanInfo` distinguishing "manual upload, AI queued" from "Integration Hub scan, AI never runs," so a scan open past the window looks the same whether it never had AI to begin with or its AI step genuinely failed; the WebApp logs are still the way to tell those apart.
- **The background queue remains purely in-memory and single-worker.** A queued item is lost if the app restarts before it runs, and items are processed strictly one at a time, so a burst of uploads queues up AI calls rather than running them concurrently. This was true of the original fix and is unchanged by the polling UI above; not a regression from the synchronous design (which had no queue, retry, or concurrency story at all), but still not a complete solution.

## Alternatives considered
- ~~**Make the AI step optional and asynchronous**, e.g. a background job triggered after the scan is saved, with the UI polling or refreshing the AI tab when a result becomes available, and a per-scan or global toggle to skip it entirely.~~ **Adopted in full.** Both halves are now implemented: the asynchronous background job with UI polling (via `IBackgroundTaskQueue`/`QueuedHostedService`), and a *global* (not per-scan) toggle -- `EngineSettings.AiAnalysisEnabled`, set on `AdminPanel/Settings`' AI Analysis tab (originally its own `AdminPanel/AIEnhancedReviewEngine` page -- see ADR-0007's 2026-11-05 entry) -- see the now-resolved "No opt-out" gap above. A per-scan toggle (letting a reviewer skip AI for one specific upload while leaving it enabled globally) was not implemented; nothing in the current requirements calls for that finer granularity.
- ~~**Run the AI step for all ingestion paths, not just manual upload**, for consistency. Not done, likely deliberately scoped to manual upload first as the lower-volume, interactive path, but this should be an explicit product decision rather than an implicit one.~~ **Adopted.** The user decided AI analysis should extend to Integration Hub-ingested scans too, resolving `Path to v1.0.md` item 28 -- see the now-resolved "Asymmetric with the other ingestion paths" gap above for what changed.
- **A durable, persisted queue (e.g. a database-backed outbox table, or a real message queue)** instead of the in-memory `Channel`-backed queue actually implemented. Not done for this fix, to keep the change minimal and self-contained; worth revisiting if queued-but-not-yet-run AI analyses being silently dropped on an app restart becomes a real operational concern.
