# 0005. Integration Hub as two ingestion paths: FTP-polling Worker Service and API-key-authenticated HTTP API

Status: Accepted
Date: 2026-09-01 (reconstructed from the v0.6 codebase)

## Context
Some source systems can only deliver audit trail exports to a location like an FTP drop; others (or scripts/tooling built around them) can make an outbound HTTP call directly. Both patterns needed to be supported without requiring reviewers to manually upload every file through the web UI.

## Decision
Build two independent front doors, both funneling into the same shared `ScanProcessingService.ProcessFileAsync` (see ADR-0003):

- **FTP Worker Service** (`Worker.cs`, hosted from `AuditTrailReview.IntegrationHub.WorkerService`): a `BackgroundService` that polls a configured FTP folder every `PollingIntervalSeconds`, claims and dedups new files against a persisted `dbo.IngestedFile` table (see "Negative / known gaps" below for how this tracking evolved), downloads and processes them tagged with a configured `SystemId`, and -- as of 2026-09-15 -- moves each file server-side into a `ProcessedFolder` subfolder on success or a `FailedFolder` subfolder once its retries are exhausted, so the drop folder itself only ever shows files still awaiting processing.
- **HTTP API** (`AuditTrailReview.IntegrationHub.API`, `ScanProcessingController`): a `POST /api/ScanProcessing/scan` endpoint authenticated by a static `X-Api-Key` header checked against a configured key list, accepting a multipart file upload plus an optional `systemId` query parameter. The bundled `AuditTrailReview.Console` CLI is simply a thin HTTP client for this endpoint.

Both paths validate that the target system exists before saving (throwing/`InvalidOperationException` otherwise). Since both ultimately call the shared `ScanProcessingService.ProcessFileAsync`, both also trigger the same AI-analysis step the manual web-upload path uses (see ADR-0006).

**API key storage, changed 2026-11-05:** the static key list is no longer a configured value at all. Keys now live encrypted (`AuditTrailReview.Engine.Security.ApiKeyProtector`, AES-256-GCM) in a new `dbo.ApiKeyCredential` table, generated and revoked from the WebApp's `AdminPanel -> Settings -> API` tab rather than hand-edited into `appsettings.json`; `ApiKeyAuthenticationHandler` now queries that table per request instead of reading a static `ApiKeyAuth:Keys` list, so a revoked key stops working immediately with no restart. This also fixed a related gap the MCP server shared (ADR-0010): the two services previously each carried their own static key list with no structural reason a key couldn't be reused across both; they now draw from two separate tables (`ApiKeyCredential` here, `McpApiKeyCredential` for the MCP server) that share the decrypt/compare logic (`ApiKeyCredentialValidator`) but never each other's keys.

**API documentation exposure, confirmed 2026-09-02:** Swagger UI and the generated OpenAPI document (`app.MapOpenApi()`, `app.UseSwagger()`, `app.UseSwaggerUI()`, and the `/` → `/swagger` redirect in `AuditTrailReview.IntegrationHub.API/Program.cs`) stay gated behind `app.Environment.IsDevelopment()`, as they already are today -- not reachable in a production deployment. This was decided rather than left as an open item (see `Path to v1.0.md` item 26): the API is authenticated by a small set of static, long-lived keys rather than per-caller accounts (see "Negative / known gaps" below), so it is already a comparatively soft target; publishing a live, browsable schema of every endpoint and payload shape to anyone who can reach the host would hand an attacker free reconnaissance with no offsetting benefit to a legitimate integrator, who gets the API contract from the Technical Manual / `TechStack.md` instead. This also matches the general GxP preference for a validated production environment carrying the minimum extra tooling/surface needed to run, not developer conveniences left switched on by default. If a genuine need for a browsable production API reference emerges later, it should be served as a static, versioned document rather than by enabling Swagger for the live service.

## Consequences

**Positive:**
- Either integration style can be adopted per source system without forcing every vendor integration through the same mechanism.
- Both paths share the same system-existence validation and rule evaluation as each other (see ADR-0002, ADR-0003), so a scan looks and behaves identically in the UI regardless of which door it came through.
- The API's key-based auth is simple to reason about and to rotate independently of the WebApp's Identity-based user accounts.

**Negative / known gaps:**
- ~~The FTP Worker Service's "already processed" tracking is in-memory only~~ ~~**Fixed.** `FtpFileCheckerService` no longer keeps an in-memory `HashSet<string>` of seen file names. On each poll it checks the `Scan` table...~~ **Superseded, 2026-09-14.** The `Scan`-table check above closed the in-memory-only gap but had a gap of its own: `ScanProcessingService.ProcessFileAsync` saves the `Scan` row *before* generating and saving its `ScanResult` rows, so for a large file a crash in between left a `Scan` row on disk with zero results, invisible to that check as "still needs doing," permanently. Dedup now runs against a dedicated `dbo.IngestedFile` table (`AuditTrailReview.Model.IngestedFileInfo`) instead: `FtpFileCheckerService` claims a file (writing an `IngestedFile` row as `Processing`, saved immediately) *before* downloading or processing it, and flips it to `Completed` (with the resulting `ScanId`) or `Failed` (with the exception message) once `ProcessFileAsync` returns. A row still `Processing` when the Worker Service starts up can only mean the previous run was killed mid-file (this pipeline is single-instance and strictly sequential, and the polling loop fully awaits every discovered file before it can start another poll), so `Worker.cs` now resets any such row to `Pending` once at startup (`FtpFileCheckerService.RecoverStuckClaimsAsync`) rather than leaving it stuck or silently skipping the file; a genuinely `Failed` file (an exception, not a crash) is retried up to 3 times before being left alone. Separately, `ProcessFileAsync`'s two saves are now wrapped in one database transaction, so the half-saved `Scan`-with-zero-results state that originally motivated this change can no longer occur at all, regardless of which table dedup reads from. Dedup itself still relies on checking the database rather than a file's location on the FTP server. **Update, 2026-09-15 (the "no write/rename permissions needed" rationale below no longer fully holds):** at the user's request, `FtpFileCheckerService` now also moves each file on the FTP server itself, purely for admin/IT visibility and cleanup, independent of and after the dedup decision above has already been made and persisted -- a successfully processed file is moved into a configurable `ProcessedFolder` subfolder (default `Processed`), and a file that has exhausted `MaxRetryAttempts` (3) is moved into a configurable `FailedFolder` subfolder (default `Failed`, alongside its recorded `IngestedFileInfo.ErrorMessage`) so it stops cluttering the drop folder once it will never be retried again. Either subfolder is created automatically the first time it's needed, and either move can be disabled independently by setting its setting to an empty string. This means the FTP account configured in `Ftp:Username`/`Ftp:Password` now needs write, rename, and create-directory permission in `RemoteFolder`, not just read/download, to get the benefit of this feature -- see `Installation Manual.md` §8. A read-only FTP account still works for ingestion itself (the dedup/processing decision never depended on being able to move files), it just can't benefit from this housekeeping: a failed move is caught, logged as a warning, and does not affect the scan or the file's `IngestedFile` status either way. **Follow-up, 2026-09-15:** because a `Completed` or retry-exhausted `Failed` row is deliberately excluded from the normal per-poll retry logic, a file whose one-shot move failed the first time (a transient FTP error, the account temporarily lacking write permission, etc.) would otherwise sit in `RemoteFolder` forever with no further attempt to relocate it. `FtpFileCheckerService.CheckForNewFilesAsync` now also runs a throttled sweep (`FtpSettings.StaleFileCheckIntervalMinutes`, default 60 minutes between sweeps) that finds any file still in `RemoteFolder` whose `IngestedFile` row says it should already have moved and has sat that way for longer than `FtpSettings.StaleUnmovedFileThresholdMinutes` (default 60 minutes), and retries the move for it -- reusing the same file listing and database lookup the poll already fetched, so this adds no extra round trip except when something is actually stale. **Follow-up, 2026-09-15:** a user-reported `550` `FtpCommandException` on this move turned out not to be the FTP account's permission (confirmed by the user: `RemoteFolder` has write/read rights, and moves to `ProcessedFolder` had worked before) but a destination-already-exists conflict -- FTP's `RNTO` rename has no standardized, guaranteed overwrite behavior, and several server implementations reject a rename onto a path that already has a file there (`550`) rather than silently replacing it. `TryMoveFileAsync` now explicitly checks `FileExists` on the destination path and deletes it first, rather than relying on `FtpRemoteExists.Overwrite` alone; a `550` that still occurs after this fix is now logged with an additional line ruling out the destination-exists cause specifically, to steer troubleshooting toward source-folder permission instead of restarting the same permission investigation from scratch.
- ~~The API has no rate limiting~~ **Fixed (NFR-005).** `AuditTrailReview.IntegrationHub.API`'s `Program.cs` now applies ASP.NET Core's built-in rate limiter (`System.Threading.RateLimiting` / `Microsoft.AspNetCore.RateLimiting` -- no extra NuGet dependency) as a global, fixed-window limit, configurable via the `RateLimiting` section (`PermitLimit`/`WindowSeconds`, default 60 requests/60s in production). It runs before authentication, is partitioned per caller -- by the raw `X-Api-Key` header value when one is present, so each configured key gets its own independent budget rather than one busy integration starving the others, or by remote IP when the header is missing/unrecognized, so an unauthenticated caller (e.g. someone probing for a valid key) is still bounded -- and returns `429 Too Many Requests` with a `Retry-After` header on rejection. **Still open:** no per-caller identity beyond a shared key, and no request auditing beyond standard logging, so anyone with a valid key can still submit on behalf of any `systemId`, and a key is shared identity, not an individual one. ~~The shipped default key (`change-me-api-key`) must still be changed before production use.~~ **Confirmed changed in production, 2026-09-02** (`Path to v1.0.md` item 2) -- the checked-in `appsettings.json` still ships the placeholder by design (it's the template default for a fresh install), and the real production key is a per-deployment secret that isn't and shouldn't be in this repo. **Superseded, 2026-11-05.** There is no longer a placeholder key in `appsettings.json` to forget to change: `ApiKeyAuth:Keys` was removed entirely, and `dbo.ApiKeyCredential` starts empty on every install, so an API key only ever exists once an admin deliberately generates one. The rate limiter's per-key partitioning above is unaffected (it still partitions by the raw presented `X-Api-Key` header value, not by looking the key up).
- **Fixed, 2026-09-15 -- API had no explicit upload-size limit or client-timeout headroom for large files, unlike the WebApp.** `ScanProcessingController` had no `[RequestSizeLimit]`/`[RequestFormLimits]`, so it fell back to Kestrel's/IIS's default request-body cap (~30,000,000 bytes / ~28.6 MiB) -- well below the ~42 MB / 300k-record ceiling `AuditTrailReview.WebApp`'s `Scan.cshtml.cs` explicitly supports against the same `ScanProcessingService.ProcessFileAsync`. A genuinely large file posted to the API was rejected outright, purely by omission. Separately, the bundled `AuditTrailReview.Console` client called the API with a plain `new HttpClient()` (default 100-second timeout) -- shorter than even the smallest benchmarked file (50k records, ~2:00) -- so it would give up before the server finished regardless of the size cap. Both are fixed: `ScanProcessingController` now carries the same 50,000,000-byte cap as the WebApp (applied directly to the action method -- the Razor-Pages-only restriction on these attributes doesn't apply to MVC controllers), a matching `web.config` was added for the (currently unused) IIS-hosting path, and the Console client's `HttpClient.Timeout` is now 20 minutes. The Worker Service was never affected by either issue, since FluentFTP downloads bypass the HTTP request pipeline entirely.
- **Changed -- the API no longer processes uploads synchronously.** `ScanProcessingController` validates the request (400 for an empty file, over-long name, unsupported extension or unknown `systemId`), stores the file as a `Tier.Worker` `ScanUploadJob` and returns `202 Accepted` with a `jobId`; the Worker Service does all processing. This removes the size-based tiers and in-process queue from the API and means a queued upload survives an API restart, at the cost of a mandatory Worker Service next to the API, up to one poll interval of extra latency, and callers having to poll `GET /api/ScanProcessing/scan/{jobId}` (the Console client does).
- **Two independent copies of "does this system exist" and "which rules ran" behavior** exist only because both paths call the *same* `ScanProcessingService`; if a future change adds a third bespoke ingestion path that doesn't reuse it, this consistency guarantee would need to be re-established deliberately.
- Neither path currently exposes health-check or ingestion-lag metrics (e.g. "how long since the last successful FTP poll," "how many files failed to process") for monitoring.

## Alternatives considered
- **A single unified ingestion API with FTP as a scheduled job that calls it internally**, rather than two separate code paths both calling `ScanProcessingService` directly. Would reduce the Worker Service to a thin scheduler on top of the same HTTP surface external systems use. Not implemented; the current design achieves most of the same consistency benefit by sharing the service layer directly (in-process) rather than over HTTP, avoiding an unnecessary network hop for the FTP path.
- **SFTP/cloud-storage connectors in addition to FTP** were not built in this baseline; the architecture (both ingestion paths converging on `ScanProcessingService`) is intended to make adding one straightforward later.
